# 0022: Recipe Translation Provenance, Editorial Tracking, and Machine Overwrite Protection

We decided to introduce a relational translation provenance tracking subsystem with the `TranslationSource` enum (`author_original`, `machine`, `manual`) on `RecipeTranslation`, automatically tag provenance on recipe creation and localized mutation hooks, protect manually curated translations from automated machine overwrite during retranslation and retry passes, and expose provenance in `RecipeProjection` detail envelopes and OpenAPI contracts.

## Context

1. **Multilingual Ingest & Moderation Ambiguity**: In WeCook, recipes are authored in a primary source language (e.g. Italian) and automatically projected across supported platform languages (English, French) via LibreTranslate. Previously, all translation rows were stored uniformly without tracking lifecycle origin. Consequently, moderators auditing reported content could not determine whether an offensive or inaccurate term was written by the recipe author or hallucinated by the translation model.
2. **Editorial Curation Invisibility**: Authors and platform staff can edit translations to refine culinary terminology and idiomatic clarity. Without origin metadata, readers could not gauge whether instructions were human-verified or raw machine output.
3. **Vulnerability to Automated Overwrite**: During recipe updates where canonical source text is edited with retranslation enabled (`retranslate: true`), or when invoking translation retries on failed recipes, background translation workers blindly overwrote all target locales, obliterating any prior handcrafted human curation.

## Decision

1. **Relational Data Model Extension**:
   - Add `TranslationSource` enum to PostgreSQL and Prisma:
     ```prisma
     enum TranslationSource {
       author_original
       machine
       manual
     }
     ```
   - Add `translation_source TranslationSource @default(machine)` to `RecipeTranslation`.

2. **Creation Lifecycle Tagging (`RecipeService.createRecipe`)**:
   - During atomic recipe insertion, the translation matching `recipe.source_lang` is explicitly created with `translation_source: TranslationSource.author_original`.
   - Synthesized translations from `TranslationService.translateBatch` are created with `translation_source: TranslationSource.machine`.

3. **Editorial Mutation Hooks (`RecipeService.updateRecipe`)**:
   - In `PATCH /api/recipes/:id`:
     - If text attributes (`title`, `description`, `preservation`, `tips`) for a non-source locale are provided, the translation is updated (or upserted) with `translation_source = TranslationSource.manual`.
     - Modifications to the recipe's `source_lang` locale preserve `author_original`.
     - Modifications strictly affecting non-translation attributes (e.g. `prep_time`, `servings`, `difficulty`) leave translation provenance completely untouched.

4. **Machine Overwrite Protection**:
   - In `RecipeService.updateRecipe` (retranslation pass) and `RecipeService.retryFailedTranslations`:
     - Inspect existing target locale translation records prior to executing LibreTranslate updates.
     - Translations marked `manual` or `author_original` are strictly protected and skipped, preventing automated workers from overwriting human curation.

5. **API Projection & Documentation**:
   - Enrich `LocalizedRecipeDetailResponse` (`RecipeDetailDto`) with `translation_source: TranslationSource` for the resolved active locale.
   - Update `available_languages` in detail responses to project array of `{ locale: string, translation_source: TranslationSource }` items (`AvailableLanguageResponse`).
   - Sync OpenAPI 3.0 specification (`openapi.json`) and Postman collection (`wecook-api.postman_collection.json`).

## Consequences

- **Auditing Clarity**: Platform moderators can immediately discern whether reported text was authored by a human or generated by machine translation.
- **Data Protection**: Handcrafted translations edited by authors or staff are safeguarded against accidental automated destruction during retranslations.
- **Contract Stability**: Projection decoupling ensures summary cards in listings and feeds remain lightweight while detail views surface full provenance transparency.
